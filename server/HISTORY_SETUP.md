# Navigation history backend

The existing public.UserHistory table is used without migrations:
- User_id -> user.id
- Building_id -> building.building_id
- Location_id -> location.location_id (nullable for a building destination)
- id is generated by the database; created_at defaults to now().

Set SESSION_SECRET to a cryptographically random value of at least 32 characters
in server/.env and in the deployment environment. Use the same secret for all
backend workers. Never commit it. A local secret has been configured in the ignored
.env file. Restart FastAPI, then log in again (or sign up) to receive a session.
Sessions expire after 24 hours. The app holds the token in memory and clears it
on logout; it does not persist the token in shared_preferences.

GET /history?offset=0 returns pages of 100, newest first.
POST /history accepts buildingId and optional locationId.
DELETE /history/{id} deletes one owned record; DELETE /history clears owned records.
Every endpoint requires a signed Bearer session. User_id is derived from the token,
never accepted from the request body. The server checks room/building membership.
Configure SUPABASE_KEY with server-side access to these tables. Do not expose that
key in Flutter. Direct database access is still governed by your Supabase grants
and RLS; this change does not modify those policies.

Preview and Start each trigger saving, but a preview followed by Start in the same
selection session saves only one destination record. Completed/ended statuses are
not saved because the existing table has no status column. History shows the joined
destination/room names and original timestamp. Old device-only history is not
silently migrated. Names reflect the current database records.

Get directions from a history card opens starting-point selection and retains the
room destination. Other origins allow Preview only; Current Location allows Start.
The internal comfortableShaded enum/API value stays unchanged for compatibility;
the visible label is Shaded Path.

Validation uses mocked database writes and real read-only schema/query checks.
A successful real insert still depends on the table's id identity/default and
server-key permissions; no real user's history is inserted or deleted by tests.
